# OpenADR 3 type and data validation definitions

This directory is meant to be a project providing good quality type declarations, and data validation functions, for the OpenADR 3 specification.

OpenADR 3 is defined by the OpenADR Alliance (https://www.openadr.org/).  It is a modern REST-style API defined using an OpenAPI 3 YAML file, plus a set of JSON schemas.  The specification is only available to those who register with the Allaince.  Because I am part of the technical team steering the OpenADR 3 project, I have a copy of the specification on my disk.

The specification is located in the directory ../specification

The OpenADR 3.1.0 specification is current, and is located in the directory ../specification/3.1.0

The intention is to provide libraries for the following programming platforms:

* `./node` - Targeting the Node.js platform, using TypeScript to define data types, and either Joi or Zod to provide data validation functions.  This is to be portable for Node.js, Deno, and Bun runtime engines.
* `./python` - Targeting the Python 3 platform.
* `./go` - Targeting the Go platform.
* `./rust` - Targeting the Rust platform.
* `./zig` - Targeting the Zig platform.

You will find currently a directory named `./node-old`.  This contains:

* `./node-old/builder` - Scripts for building code artifacts from the OpenADR 3 specification
* `./node-old/package` - A Node.js package for the data types and data validation functions.  Most of the code is built using the scripts in the builder directory.
* `./node-old/test` - A test suite for exercising the functions.

# Architecture

For each of the targeted programming platforms, a directory is to exist with the following components:

* `builder` - Directory containing scripts to build code artifacts from the OpenADR 3 specification and JSON schemas
* `package` - Directory containing the code for a package that is to be capable of being distributed through the package management system for the programming platform.
* `test` - Test code for the package.
* `docs` - Documented, most of which would be autogenerated.

Data types must be defined from the schema definitions in `../specification/3.1.0/openadr3.yaml`. The data types come from these areas:

* The `components/schemas` section, which contains schema declarations for each object.  
* Within the `paths` section:
    * Some API endpoints have `parameters`, and the parameters can be converted into a data type describing all the parameters.
    * The API endpoints have `responses`, each of which can be converted into a data type.

The data types must be declared for ease of use by developers.

The data validation functions must correspond to the data types.  A validation function takes an anonymous object, examines the object to see if it is compatible with the data type, and returns either a success or failure result.  The failure result should contain one or more error objects describing the errors found.  The success object should be the supplied object, but with the correct data type.
